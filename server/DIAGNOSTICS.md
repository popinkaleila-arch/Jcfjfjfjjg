# Диагностика сервера 31.76.30.135 (`child-wooden.vpspay.net`)

Дата обследования: 6 октября 2026, ~03:30–04:10 EEST.

## Коротко

Сервер находился в состоянии полного отказа по памяти: своп был израсходован
на 100 %, ядро тратило 98–99 % процессорного времени на подкачку, OOM-killer
убивал боты каждые несколько минут. Причина — утечка процессов драйвера
Playwright в боте `remanga-autobattle`, накопившая 33 зависших процесса за
36 часов. Первопричина утечки — отсутствующие на диске браузеры Playwright.

После устранения load average упал с 42 до 0.55, своп освободился на 1.5 ГБ.

Попутно выяснилось, что `remanga-autobattle` был полностью нерабочим и по
другой причине: автологин на MangaBuff ломался из-за оверлея на странице
входа, поэтому бот получал `http_401` на любой запрос. Это тоже исправлено —
бот авторизуется и работает.

## Причина отказа

1. На диске не было ни одного браузера Playwright: каталог
   `/root/.cache/ms-playwright/` отсутствовал целиком. В логе
   `remanga-autobattle` на каждый запуск:
   `Executable doesn't exist at /root/.cache/ms-playwright/chromium_headless_shell-1228/...`
2. `MangaBuffService.start()` сначала поднимал node-драйвер Playwright
   (`async_playwright().start()`), и только потом запускал браузер. Падение
   запуска браузера пробрасывалось наружу, минуя очистку: ссылка на драйвер
   терялась, а сам процесс оставался жить.
3. Планировщик вызывал `start()` раз в час (обслуживание рынка) и раз в два
   часа (торговый цикл). Отсюда ровный ритм утечки: один зависший процесс в
   нечётный час, два — в чётный. Фактические метки времени это подтверждают:
   16:00 → 2, 17:00 → 1, 18:00 → 2, 19:00 → 1 и так далее.
4. За 36 часов накопилось 33 процесса по 30–90 МБ RSS и 70–140 МБ свопа
   каждый — порядка 2.5 ГБ. `Committed_AS` достиг 7.4 ГБ при `CommitLimit`
   3.1 ГБ.
5. Дальше пошёл каскад: своп исчерпан → непрерывная подкачка → процессор
   полностью занят ядром → OOM-killer. Счётчики перезапусков:
   `channel-reposter` 70, `tg-pool` 61, `starvell-cardinal` 24,
   `FunPayCardinal` 9. SSH тоже перестал успевать отдавать баннер — именно
   поэтому подключение к серверу сначала обрывалось по таймауту.

## Что сделано

### 1. Освобождена память

`systemctl restart remanga-autobattle` — systemd снял всю cgroup сервиса
вместе с 33 зависшими процессами. Освободилось 2 ГБ свопа и 790 МБ RAM.

### 2. Установлены браузеры Playwright

```bash
HOME=/root /root/remanga_autobattle/.venv/bin/python -m playwright install chromium  # 1.61.0 → ревизия 1228
HOME=/root /opt/dwar_venv/bin/python -m playwright install chromium                  # 1.62.0 → ревизия 1234
```

`dwar_bot` ещё не упирался в эту проблему только потому, что не запускал
браузер, но его venv был ровно в таком же состоянии.

Проверено запуском: Chromium 149.0.7827.55 поднимается, бот реально ходит
по страницам.

### 3. Закрыта утечка в коде

`services/mangabuff_service.py` — `fixes/mangabuff-playwright-driver-leak.patch`.
Запуск браузера обёрнут в `try/except BaseException`, при сбое вызывается
новый метод `_discard_playwright()`, который закрывает контекст, останавливает
драйвер и сбрасывает флаги. `stop()` переведён на тот же метод, чтобы логика
освобождения жила в одном месте.

Проверка — `fixes/test_playwright_driver_leak.py`. Тест принудительно ломает
запуск браузера через `PLAYWRIGHT_BROWSERS_PATH` и считает дочерние процессы
драйвера:

```
ДО патча:    драйверов после сбоя: 1   _playwright is None: False   → FAIL
ПОСЛЕ патча: драйверов после сбоя: 0   _playwright is None: True    → OK
```

Резервная копия исходного файла:
`/root/remanga_autobattle/services/mangabuff_service.py.bak.20261006_005359`.

### 4. Починен автологин MangaBuff

После установки браузеров выяснилось, что бот не может войти в аккаунт:
`Locator.click: Timeout 8000ms exceeded` на кнопке «Войти», и дальше
`http_401` на инвентарь, фильтр карт и обмены. Логин и пароль в `.env` были
заданы корректно.

Разведка DOM (`fixes/mb_probe_login_dom.py`) показала, что на `/login`
соседствуют две формы входа: видимая на самой странице и её копия внутри
`#modal-auth`. Модалка открыта (`modal--open`), размеры её полей нулевые, но
поддерево перехватывает указатель — поэтому клик по видимой кнопке не
доходил. Снизу вдобавок висел баннер `#modal-tenor` без кнопки закрытия.

Исправление — `fixes/mangabuff-login-overlay.patch`: новый
`_clear_login_overlays()` снимает `#modal-auth`, `#modal-tenor` и
`.modal--fixed-bottom` перед кликом по кнопке входа. Метод вызывается только
в логине, поэтому модалки награды не затрагивает.

Проверка — `fixes/test_mangabuff_login.py`, прогон на чистом профиле:

```
БЕЗ патча: результат входа: FAIL — не авторизован   (url: /login)
С патчем:  результат входа: OK — авторизован        (url: mangabuff.ru/)
```

В бою после перезапуска: ноль `http_401` за 4 минуты, бот читает инвентарь,
набирает 240 целей для обмена и успешно отправляет предложения.

### 5. Остановлен поток отладочных логов

`/opt/starvell-cardinal/config/settings.json` содержал `"debug": true`, из-за
чего бот писал каждый SQL-запрос в журнал. Через rsyslog это вылилось в
`/var/log/syslog.1` размером 826 МБ. Флаг снят, сервис перезапущен, в логах
остался уровень INFO.

### 6. Приведены в порядок логи

Удалено около 1.1 ГБ ротированных `syslog.*`, `auth.log.*` и `btmp.*`.

Добавлены два конфига (`ops/`):

* `journald-99-size-cap.conf` → `/etc/systemd/journald.conf.d/99-size-cap.conf` —
  потолок журнала 200 МБ, хранение неделю, ограничение частоты записи.
* `logrotate-bots` → `/etc/logrotate.d/bots` — ротация логов `dwar_bot`
  (`systemd_stderr.log` вырос до 25 МБ без ротации), `Hikka` и
  `remanga_autobattle`.

### 7. Закрыт SSH от перебора

В `auth.log` за двое суток — 20 962 неудачные попытки входа. Топ источников:
`77.239.124.154` (1025 попыток) и подсеть `109.160.32.0/24` (около 1000
попыток с каждого из десятка адресов). Ни firewall, ни fail2ban не было,
при включённом входе root по паролю.

Признаков взлома нет: за двое суток всего четыре успешных входа — IP
владельца и два адреса этого агента.

Установлен fail2ban с конфигом `ops/fail2ban-jail.local` → `/etc/fail2ban/jail.local`
(jail `sshd` в режиме `aggressive`, 4 попытки за 10 минут, бан на 2 часа).
За первые 10 секунд работы забанил 3 адреса, за первый час — 20.

### 8. Настроена подкачка под объём памяти машины

`ops/sysctl-99-low-memory-host.conf` → `/etc/sysctl.d/99-low-memory-host.conf`:
`vm.swappiness` снижен с 60 до 10, `vm.vfs_cache_pressure` с 100 до 50. При
стандартных значениях ядро на этой машине начинало выталкивать рабочие
страницы в своп задолго до реальной нехватки памяти.

### 9. Разобраны последствия падений

* Сняты состояния `failed` у `unattended-upgrades.service` и `user@0.service` —
  оба были убиты OOM-killer во время кризиса. `unattended-upgrades` запущен.
* `FunPayCardinal@fpc.service` **не был включён в автозапуск**: после любой
  перезагрузки бот не поднялся бы. Включён. Теперь все восемь сервисов
  (`channel-reposter`, `remanga-autobattle`, `dwar_bot`, `starvell-cardinal`,
  `tg-pool`, `FunPayCardinal@fpc`, `redis-server`, `fail2ban`) и активны, и
  включены в автозапуск.

## Что осталось и требует решения владельца

1. **Проект ВК-бота на сервере отсутствует.** Полный поиск по диску
   (`import vk` / `vk_api` / `vkbottle` / `api.vk.com` / «ВКонтакте») не дал
   ни одного совпадения в коде. Упоминания `vk.com` встречаются только в
   списках разрешённых ссылок SMM-плагина `vexboost_autosmm.py`. На GitHub
   у связанного аккаунта тоже один пустой репозиторий.

2. **Платёжные данные опознаны как Platega, но целевого бота здесь нет.**
   Мерчант называется «Paskod VPN», а продающий бот — `@PaskodVPN_bot`.
   На этом сервере он только рекламируется из `tg_pool`
   (`promote_username = "@PaskodVPN_bot"`), кода самого бота нет. Готовый
   проверенный клиент лежит в `integrations/platega.py`.

3. **Нужна перезагрузка.** Работает ядро 6.8.0-136, а установлено уже
   6.8.0-142; в очереди обновления `libc6`, `apparmor` и четыре версии ядра,
   система держит флаг `*** System restart required ***` при uptime 67 дней.
   Я не перезагружал сервер сам, чтобы не ронять боты без ведома владельца;
   автозапуск у всех сервисов теперь проверен, так что перезагрузка
   безопасна.

4. **Ошибка в плагине FunPayCardinal.** `[KOSellRent] set_lot_active ... failed
   после 4 попыток: 'NoneType' object is not subscriptable` — повторяется для
   лотов 73552629, 73552631, 73552632, 73552634. Плагин не обрабатывает
   пустой ответ FunPay.

5. **Конкуренция за браузер в `remanga-autobattle`.** В логах появляется
   `MangaBuff browser lock timeout (cycle 1 catalog)`: часовая задача
   обслуживания рынка и двухчасовой торговый цикл делят один браузер и
   иногда не дожидаются блокировки. Поведение существовало и до правок,
   данные не теряются — цикл просто пропускается.

6. **Ресурсов машины мало.** 1 vCPU и 2 ГБ RAM на семь ботов, два из которых
   гоняют Chromium, не оставляют запаса: даже в здоровом состоянии свободно
   около 1 ГБ. Любой второй браузер снова упрётся в своп. Разумный минимум —
   2 vCPU и 4 ГБ.

7. **Вход root по паролю открыт в интернет.** `PermitRootLogin yes` и
   `PasswordAuthentication yes`. Рекомендуется завести SSH-ключ и выключить
   парольную аутентификацию — я этого не делал, чтобы не отрезать доступ.

8. **Секреты скомпрометированы передачей в открытом виде.** Пароль root и
   ключ Platega стоит сменить после завершения работ.
